# 05 · 待决策与风险

## 一、需要拍板的问题

这几个问题会**实质性改变设计**，需要先确定：

### 1. 她的动机是什么？
- [ ] 纯兴趣
- [ ] 学校信息技术课要用
- [ ] 想做点自己的作品
- [ ] 长远考虑（升学 / 职业）

👉 影响：项目题材偏娱乐（游戏、绘画、聊天机器人）还是偏实用（成绩统计、记账、数据分析）。

### 2. 每天想让她花多久？
- [ ] 20 分钟 —— 知识点更碎、项目更小、总天数拉长
- [ ] 40 分钟 —— 能做出像样的东西，成就感更强

👉 影响：每天的知识点密度和项目规模。

### 3. 要不要家长视图？
- [ ] 要，而且明确告诉她有
- [ ] 要，但做成"每周一起看的周报"
- [ ] 不要

👉 影响：后端复杂度，以及更重要的——信任关系。

### 4. 视觉化功能的优先级
`turtle` 画图和 `matplotlib` 图表是额外工作量（turtle 需要自写 Canvas shim），
但对青少年的吸引力很大。

- [ ] 值得，排进第 7 阶段
- [ ] 值得，甚至提前到第 2 阶段（用画图来教循环，效果极好）
- [ ] 先不做

## 二、主要风险

### 🔴 风险 1：内容量（最大风险）

70 天 × (讲解 + 项目 + 3 级提示 + 判题用例 + 4 道练习) 是实打实的工作量。
**这不是技术风险，是持续投入的风险。** 网站做好了但内容只有 5 天，等于没做。

**对策**：见下面的落地节奏。

### 🟡 风险 2：难度曲线失控

设计者（会编程的人）几乎必然会低估某些知识点的难度。
典型高危点：变量赋值 `x = x + 1`、循环的执行顺序、函数的参数传递、类和对象的关系。

**对策**：错题本 / 卡壳记录不只是给她用的，更是**给你用的**——
哪一天她提示用得多、报错次数多，就说明那一天的讲解写坏了，回去改。

### 🟡 风险 3：她根本不想学

再好的产品也没法解决动机问题。

**对策**：
- 前 3 天必须做出"哇"的效果（做一个能跟她对话的东西，而不是 `print("Hello World")`）
- 作品能分享给你看，这个社交反馈可能比学习本身更有驱动力
- 允许她跳过、允许她断签、允许她自己改需求做点别的

### 🟢 风险 4：技术坑

`input()` 和 `turtle` 两个坑已在 [04-技术架构](04-技术架构.md) 中标明，都有明确解法。
其余基本是常规工程。

## 三、推荐的落地节奏

### 阶段 A：跑通闭环（先做这个）
- 全部核心功能跑通：编辑器 + Pyodide 运行 + 判题 + 中文报错翻译 + 进度保存
- **只写 10 天的完整内容**
- docker compose 能起来

### 阶段 B：真实使用 + 观察
让她真的用 10 天。观察：
- 她卡在哪个知识点
- 她喜欢哪类项目
- 哪些功能她根本没点过
- 她每天实际花多久

### 阶段 C：按反馈补内容
再决定后面 60 天怎么写。

> **她的真实反馈比现在的任何推测都值钱。**
> 不要一口气写完 70 天内容再给她——那样错了要改 70 天份。
